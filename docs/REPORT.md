# 중고 매물 → 정식 제품명 정규화: 방법 조사 + 아이폰/갤럭시 실측 (2026-10-08)

> 목표: `"구매하실분들만 연락주세요아이폰 12 미니 네이비 128GB 풀박스 상태좋아요"` →
> `{아이폰, 12, 미니, 네이비, 128GB}`처럼 사람들이 검색할 수 있는 구조화 데이터로 만든다.
> 조건: 학습 최소화, 최신 모델로 쉽게 교체 가능.

실험 기록 전체다. 최종 결과와 실행법은 [README](../README.md)에 있고, 저장소에는 최종 파이프라인(8~9절) 코드만 넣었다.
1~7절의 비교 실험(vLLM 프롬프트, Laya, 인코더 등)에 쓴 코드는 넣지 않았다.

## 0. 결론 (TL;DR)

- **추천 방식은 규칙·사전 + 소형 LLM(4B급) + 제품 카탈로그를 결합한 하이브리드다. 학습은 0회다.**
  - 프롬프트에는 few-shot 예시 8~11개를 넣고 JSON 스키마로 출력을 강제한다.
  - 카탈로그는 LLM이 낸 모델명을 검증하고, 정식 이름을 `{브랜드, 라인, 세대, 변형}`으로 분해한다.
- **실측 결과** (폰 판매·구매글에서 모델명·용량·색상 3필드 완전 일치율)
  - 새 테스트셋(test2, 119건): 하이브리드(Qwen3.5-4B) **91.6%**. 규칙만 쓰면 75.6%.
  - 필드별: 모델명 95%, 용량 100%, 색상 96.6%, 글 유형 96%, 카테고리 97%.
  - 정답셋 300건 전체에서도 90.4%로 결과가 일관된다.
- **모델 크기 비교**
  - 4B급(Qwen3.5-4B, Gemma-4-E4B)이 최적점이다.
  - 9B·12B로 키우면 +0~1pt에 그치고 속도는 절반이다.
  - 0.8B~2B는 규칙과 비슷하거나 그보다 못하다.
  - few-shot 예시는 +3~4pt 효과가 있다.
- **Laya는 이 과제에 맞지 않는다.**
  - 텍스트를 생성하지 않고 "주어진 선택지"에 점수만 매기는 모델이라 모델명·용량·색상 같은 열린 값을 뽑을 수 없다.
  - 한국어 zero-shot 실측에서 글 유형 15~68%, 카테고리 50~71%가 나와 "전부 판매글"이라고 찍는 것(93%)보다도 낮았다.
  - 그나마 쓸 수 있는 곳은 파인튜닝 후 닫힌 분류뿐이다.
- **비용과 속도**
  - 로컬 RTX 5090 + Qwen3.5-4B: 초당 26.6건(6,323건 연속 처리), 하루 약 230만 건까지 가능하다. 하루 1만 건이면 GPU 4~6분이면 끝난다.
  - API로 대체할 경우 Claude Haiku 5.5 기준 하루 1만 건이 **월 약 $17, Batch를 쓰면 월 약 $9**다(실측 토큰량 기준 계산이며 정확도는 미측정).
- **신모델 대응**
  - 카탈로그에 한 줄을 추가하면 끝이고 재학습은 없다.
  - 카탈로그에 없는 이름은 `needs_review`로 표시된다. 이번 수집에서도 "아이폰 18 듀오", "Z폴드8 와이드/울트라" 같은 미등록 표기를 실제로 잡아냈다.
  - 새 LLM이 나오면 `llm_extract.py --model <새 모델>`과 `report_table.py`로 10분 안에 비교할 수 있다.
- **신뢰도 신호**
  - 규칙과 LLM의 결과(모델·용량)가 **일치하는 87%는 정확도 95~96%**, **불일치하는 13%는 54~60%**였다.
  - 따라서 불일치 건만 큰 모델·API·사람 검수로 보내면 된다.
- **부수 발견**: 현재 스크래퍼는 세 플랫폼 모두 최신순이 아니다(부록 A).
  - 번개장터: `order=date`가 무시되므로 `sort=latest`로 바꿔야 한다.
  - 중고나라: `nso=so:dd` 파라미터가 필요하다.
  - 당근: 정렬 옵션이 없어 `createdAt`으로 직접 정렬해야 한다.

### 2.3 결과 읽는 법
- **표본 크기**: 119~218건이라 95% 신뢰구간이 약 ±4~5pt다.
  - 4B / 9B / E4B / 하이브리드 사이의 1~2pt 차이는 통계적으로 의미가 없다.
  - 구간 차이는 분명하다: **규칙(76~81%) < 2B(78~84%) < 3~4B 이상(86~91%) ≤ 하이브리드(90~92%)**.
- **두 세트의 일관성**: 300건과 test2의 순위와 수치가 비슷하다. 과적합된 결과가 아니라는 근거다.
- **프롬프트 v2**: v1보다 +0.9pt로 오차 범위 안이다. 특정 오류 패턴을 고치는 효과는 있지만 전체 수치를 크게 바꾸지는 않는다.
- **route 모드**: LLM 호출을 57% 줄이지만, 규칙의 색상 추출이 약해 정확도가 5~9pt 떨어진다. 규칙 색상을 보강하기 전에는 비추천이다.
- **처리량**: 5090에서 vLLM 오프라인 배치로 측정했다. few-shot 프롬프트는 약 1,500토큰(prefix cache), 출력은 약 40토큰이다. 실시간 단건 호출이면 지연은 수백 ms 수준이다.

## 3. 접근법별 분석

### 3.1 규칙 + 사전 (정규식 + 별칭/색상 사전) — `rules.py`
- **장점**
  - CPU 1코어로 초당 약 14,000건을 처리하고 비용이 0이다.
  - 결과가 결정적이고 설명 가능하다.
  - 아이폰·갤럭시처럼 어휘가 닫힌 영역에서는 모델명 92~93%, 용량 96~98%로 꽤 강하다.
- **약점**
  - 색상(81~89%)과 글 유형(교환·업자 광고)이 약하다.
  - 롱테일 표현("17에어", "A155", "갤럭시골든", "노트10 울트라 9H 풀커버" = 액정필름)에서 무너진다.
  - 카테고리를 전체로 넓히면 규칙 수가 폭증한다. 당근도 같은 이유로 키워드 규칙을 버렸다.
- **용도**: 단독 해법보다는 ① LLM 없이 처리할 확실한 글을 걸러내는 1차 필터, ② LLM 결과를 검증하는 장치, ③ 데스크톱 앱(GPU 없음)의 기본 엔진으로 쓴다.

### 3.2 로컬 sLM (프롬프트 + few-shot + JSON 스키마 강제, 학습 0회) — `llm_extract.py`, `prompt.py`
- **결과**
  - 4B급(Qwen3.5-4B, Gemma-4-E4B)이 정확도와 속도의 균형점이다.
  - 9B·12B로 키워도 이득이 거의 없다. 이 과제는 추론력보다 표기 규칙과 도메인 지식이 관건이기 때문이다.
  - 0.8B는 규칙보다 못하다.
- **few-shot 효과**: 예시 8개를 넣으면 4B 기준 ALL이 +3~4pt 오른다(84.7→88.0%, dev). 예시는 프롬프트 캐시로 거의 공짜다.
- **JSON 스키마 강제 디코딩**: 파싱 실패가 0건이다. 스키마가 없으면 4B zero-shot에서 2건 실패했다.
- **한국어 특화 모델**: Kanana-2-3B는 범주 분류(97%)가 좋았지만 모델명 추출은 Qwen3.5-4B보다 낮았다. 라이선스도 "자사 서비스 사용 OK, 재판매·API 제공은 별도"라 확인이 필요하다.
- **라이선스**
  - Qwen3.5, Gemma 4: Apache-2.0
  - EXAONE 4.0: 비상업
  - HyperCLOVA X SEED: MAU 1천만 미만 조건
- **배포**: vLLM 0.31이 RTX 5090(sm_120)에서 정상 동작했다. 단, `VLLM_USE_FLASHINFER_SAMPLER=0` 설정이 필요하다(nvcc 미설치). Gemma-4-12B는 bf16으로 올리면 KV 캐시 자리가 없어 FP8로 실행했다. Kanana-2-1.3B는 transformers 설정 호환 문제로 실행하지 못했다.

### 3.3 API LLM (사내 GPU 없이)
- **가격** (2026-10 공식 가격 페이지에서 확인)
  - Claude Haiku 5.5: 입력 $0.10, 캐시 읽기 $0.01, 출력 $0.50 /1M 토큰. Batch API는 50% 할인.
  - 이번 실측 토큰량(시스템+few-shot ≈1,250토큰 캐시, 매물 ≈250토큰, 출력 ≈41토큰)으로 **하루 1만 건이면 하루 약 $0.58, 월 약 $17이고 Batch를 쓰면 월 약 $9**다.
  - Haiku 4.5($1/$5)로 같은 양을 처리하면 월 약 $174다.
  - 신형 토크나이저는 한국어에서 토큰이 더 나올 수 있어 ±30% 오차를 둔다.
- **다른 저가 API** (리서치 에이전트 조사, 가격은 각 사 페이지 기준. 한국어 품질은 공개 근거가 없어 미검증)
  - Qwen3.7-flash: $0.03/$0.13
  - Upstage solar-mini4: $0.10/$0.40, 한국어 특화
  - Gemini 3.1 Flash-Lite: $0.25/$1.50
  - 모두 JSON 스키마 출력을 지원한다.
- **이번에 API를 실측하지 못한 이유**: 환경에 API 키가 없었다. 같은 `prompt.py`와 `evaluate.py`로 그대로 측정할 수 있다.
- **장점**: GPU 운영이 필요 없고, 최신 모델로 교체할 때 모델 ID만 바꾸면 된다.
- **단점**: 외부 전송이 생긴다. used-market-notifier의 "로컬 프라이버시" 정책과 충돌할 수 있다.

### 3.4 Laya (ConvAI, 2026-09-18 공개) — `laya_test.py`
- **정체**: 텍스트를 생성하지 않는 결정 모델이다. ModernBERT/mmBERT 인코더(421M / 다국어 322M)를 쓴다. 질문마다 **미리 준 선택지**에 확률을 매긴다(choice / score / yes-no). 1회 forward로 끝나 빠르다(공식 수치는 GPU 33ms).
- **구조적 한계**: "모델명·용량·색상" 같은 **열린 값을 뽑을 수 없다**. 선택지에 없는 값은 답할 수 없으므로 신모델이 나오면 선택지를 갱신해야 한다. 공식 문서도 "a free string cannot be a fixed option set", "zero-shot 결정 엔진이 아니라 특화(파인튜닝)용 베이스"라고 밝힌다.
- **실측** (다국어 체크포인트, zero-shot, 300건, CPU)

  | 질문 | 한국어 지시문 | 영어 지시문 | 참고: 다수결 기준선 / 규칙 |
  |---|---|---|---|
  | 글 유형 | 15.0% | 67.7% | 93.0% / 95.3% |
  | 카테고리 | 71.0% | 49.7% | 78.3% / 94.7% |
  | 용량(6지선다) | 60.1% | 66.5% | — / 96.3% |
  | 제품 라인(7지선다) | 74.8% | 62.8% | — |
  | 지연 | 600ms/건 | 303ms/건 | 규칙 0.07ms |

  판매글을 0.96 확률로 "buy"라고 답하는 등 보정(calibration)도 한국어에서 맞지 않았다.
- **결론**: 이 과제의 주 엔진으로는 부적합하다. 쓸 수 있는 자리가 있다면, LLM 라벨로 파인튜닝한 뒤 글 유형·카테고리 같은 **닫힌 분류**를 CPU에서 싸게 처리하는 용도다. 하지만 그 자리는 규칙(95%)이나 일반 소형 분류기도 충분히 메운다.

### 3.5 그 밖의 비생성형 방법 (조사만)
- **GLiNER 계열 NER**
  - GLiNER2.5-multi는 한국어 평가가 없고, 띄어쓰기 없는 "연락주세요아이폰"을 단어로 분리하지 못한다.
  - 한국어 GLiNER(`lots-o/gliner-bi-ko-xlarge-v1`)는 CC-BY-SA다.
- **토큰 분류 파인튜닝** (KoELECTRA, mmBERT): 학습 데이터가 있으면 가장 싸고 빠른 추론이 가능하다. 그러나 "학습 최소화" 조건에 어긋나고, 신모델이 나올 때마다 재학습해야 한다.
- **증류 경로** (2단계 옵션): LLM 라벨 수천 건으로 1~4B를 LoRA 파인튜닝하면 교사 수준에 근접한다는 보고가 있다(Mercari: gemma-2b QLoRA, 2026 연구: Qwen3-4B 파인튜닝이 교사와 동급).

### 3.6 업계 사례 (리서치 요약)
- **당근, 2025 스마트폰 시세 서비스**
  - LLM이 게시글에서 모델·용량·상태를 추출한다.
  - 그러나 LLM이 사용자의 오기("갤럭시 폴드1")를 그대로 옮기는 문제가 있어, **추출 후 정규식으로 정규화하는 단계**를 덧붙였다. 이번 실험의 "카탈로그 검증"과 같은 결론이다.
- **당근, 2026 택소노미 시스템**: 카테고리 → 속성 순서의 2단 구조다. 후보는 BM25와 임베딩으로 좁힌다. 키워드 규칙은 롱테일 때문에 포기했고, 장기적으로는 LLM 라벨로 자체 모델을 학습할 계획이다.
- **번개장터, 2022**: 제목으로 카테고리 약 700개를 예측한다(SentencePiece + GRU). 추천 채택률이 73%에서 92%로 올랐다.
- **Mercari**: GPT-4 라벨로 gemma-2b QLoRA를 학습했다. GPT-3.5보다 좋았고 비용은 약 1/14였다.
- **Xianyu (ACL 2025)**: 정규화된 속성값 사전에서 검색해 고른다. 값 생성보다 **카탈로그 매칭**을 택한 사례다.
- **공통 패턴**: 글 유형·카테고리 필터 → 속성 추출 → **카탈로그·값 사전과 매칭** → 이후 LLM 라벨로 소형 모델 증류.

| Qwen3.5-0.8B LoRA + 근거검사 (8.8천) | 95.7% | 4.5% | 86.5% | 92.8% | **98.7%** | 553ms |

| Haiku (교사, 참고) | 97.9% | 0.7% | 90.8% | 95.7% | 98.8% | 해당 없음 |

LFM 학습 곡선(근거검사 포함, 시세 버킷): 2천 93.9% → 5천 95.2% → 1만 95.9%. 아직 오르는 중이다.

### 발견
1. **작은 생성 모델은 처음 보는 모델명을 아는 이름으로 바꾼다.** S26 → S25, 아이폰 18 → 17, 아이폰 듀오 → 7 플러스로 나왔다.
   - 세대 숫자 바꾸기 증강(`distill_data.augment_number`)만으로는 거의 낫지 않았다(55% → 61%).
   - **근거 검사(`ground.py`)로 해결했다.** 모델명·용량·색상 값이 원문에 근거가 없으면(예: 세대 숫자가 원문에 없음) 그 필드는 규칙·카탈로그 결과로 바꾼다. 원문에서 뽑는 규칙은 늘 근거가 있다.
   - 신모델에서 LFM 64% → 91%, Qwen 98.7%가 됐다.
2. **Qwen3.5-0.8B는 신모델 일반화가 LFM보다 확실히 낫다**(98.7% vs 91.1%, n=49라 신뢰구간이 넓음).
   - 전체 정확도는 둘이 비슷하다(신뢰구간 겹침).
   - 라이선스: Qwen은 Apache 2.0, LFM은 연매출 1천만 달러 이하 기업만 상업 이용 가능하다.
3. **인코더 분류 + 규칙은 상태 정확도만 오르고 시세 버킷은 그대로다.** 모델명·오염 문제는 규칙 쪽에서 생긴다.
4. **CPU 속도는 충분하다.**
   - llama.cpp 4슬롯 기준 처리량: LFM 5.0건/초, Qwen 2.3건/초. 하루 수집량(약 1만 건)의 20배 이상이다.
   - CPU 출력은 GPU bf16 출력과 98~99% 같다. 프롬프트는 학습 때처럼 토큰 ID로 넘겨야 한다(BOS 차이 주의).
   - HF transformers로 CPU 추론하면 건당 9초라 쓸 수 없다.

### 다음 단계
1. eval1k 갈린 건을 사람이 검수한다(/review → eval1k). 정답이 확정되면 위 수치를 다시 잰다.
2. 서비스 후보는 Qwen3.5-0.8B(전체 1만 건 재학습) + 근거 검사 + 카탈로그다. CPU llama-server로 띄워 vLLM·GPU 의존을 없앤다. 규칙과 모델이 갈리는 건은 지금처럼 검토 필요로 둔다.
3. 학습 곡선이 아직 오르고 있으니 Haiku 라벨을 1~2만 건 더 늘려 본다.

파일: `scripts/make_eval1k.py`, `make_train.py`, `check_labels.py`, `distill_data.py`, `train_gen.py`, `ground.py`, `score.py`. 인코더 실험(`train_enc.py`)과 LFM 학습 스크립트는 저장소에 넣지 않았다.

### 학습 데이터와 결과
- 학습 데이터는 2만 9,541건이다.

  - bf16과 결과가 다른 글은 LoRA 39건, 전체 미세조정 11건이다.
  - 둘 다 점수 차이는 오차 범위 안이다.
- 표의 수치는 수집 종료 시점(2026-10-12)의 플랫폼별 수집량으로 가중한다(`scripts/score.py`).
- 브라우저 전체 경로는 다음 순서로 1,000건 모두 오류 없이 돌렸다(headless Chrome, CPU WASM).
  - 순서: JS 입력 자르기 → wllama → 파싱 → 근거 검사 → 카탈로그 → spec.
  - 원문 출력이 서버와 다른 글은 10건이다. "아이스블루"와 "아이스 블루"처럼 확률이 거의 같은 후보 사이에서 갈렸다.

  - 즉 계산 순서(병렬 처리·스레드·WASM SIMD)에 따른 미세한 수치 차이다. 점수 차이는 없다.
- 신모델 글 81건만 따로 보면 Q4가 칸 97.4%, 시세버킷 100%다. 학습에 신모델 글이 들어갔으므로 일반화 시험은 아니다.

### 브라우저 실행 (wllama)
- **연속 처리 시 멈춤 문제를 해결했다.** 원인은 llama.cpp 서버의 프롬프트 캐시다.
  - 이 캐시는 기본 상한이 8GB이고 요청마다 이전 상태를 쌓는다. 이 모델은 하이브리드(재귀) 구조라 한 건이 20~40MB다.
  - 그래서 브라우저 WASM 메모리 4GB를 74건 언저리에서 다 쓰고 `std::bad_alloc`이 났다. "Invalid magic number"는 그 뒤에 따라온 증상이다.
- wllama 3.8.1은 이 상한(`cache_ram_mib`)을 바꿀 수 없다. 그래서 옵션만 노출하는 작은 패치를 만들어 다시 빌드했다.
  - 위치: `web/wllama/` (`cache-ram.patch`, `fetch.sh`, `build.sh`).
  - 사용 설정: `cache_ram_mib: 0`, `n_ctx_checkpoints: 0`.
  - 결과: 150건 연속 처리에도 메모리가 1,869MiB로 그대로였다. 수정 전에는 25건마다 약 1GB씩 늘었다.
- Safari처럼 JSPI·memory64가 없는 브라우저용 호환 빌드도 같이 만들었다.
  - `setCompat()`으로 직접 지정해야 한다. 지정하지 않으면 CDN의 공식 빌드를 받는데, 그건 패치가 없다.
- 브라우저(CPU WASM 8스레드, headless Chrome)에서 서버(llama.cpp) 예측과 150/150건이 같았다.
  - 글당 중앙 1.0초가 걸렸다.
  - 이 서버에는 GPU가 없어 WebGPU 속도는 재지 못했다.

- 호환 빌드(Safari용)를 Chrome에서 강제로 켜고 100건을 돌렸다. 오류 없이 기본 빌드와 출력이 100/100 같았다.
  - 이 서버에는 Safari·WebGPU가 없어 실기기에서는 재지 못했다.

### `build_spec`의 모델명 대체를 소형 모델에서는 끈다
- 서비스의 `build_spec`은 LLM이 카탈로그에 없는 모델명을 내면 모델명 전체를 규칙 결과로 바꾼다. 4B LLM이 지어낸 이름을 막으려던 것이다.
- 소형 모델 출력은 근거 검사가 이미 지어낸 이름을 막는다.
  - 남는 "모르는 이름"은 주로 묶음 판매글 속 애플워치 같은 다른 제품이다.
  - 이걸 규칙 값으로 바꾸면 "아이폰 17e + 애플워치"가 아이폰 17e 단일 모델 글이 되어 시세에 섞인다.
  - eval1k에서는 3건이 바뀌었고, 칸오염이 4.1%에서 4.4%로 나빠졌다.
- 그래서 `build_spec(..., rule_fallback=False)` 옵션을 넣었다(Python·JS).
  - 모르는 이름은 그대로 두고 검토 필요만 표시한다.
  - 기본값은 그대로라 서비스 동작은 바뀌지 않는다.
  - 브라우저 경로(`specFromOutput`)는 이 옵션을 끈다.

### 규칙·카탈로그·근거 검사의 JS 판 (`web/normalizer/`)
- `rules.js`, `catalog.js`, `common.js`, `ground.js`, `pipeline.js`는 Python 판을 그대로 옮겼다. `model.js`는 프롬프트, 출력 파싱, wllama 실행을 맡는다.
- Python과 JS 정규식의 차이를 `py.js`가 맞춘다.
  - `\w` `\d` `\b` `\s` `.` `$`의 유니코드 처리가 다르다.
  - 문자열 자르기 단위가 다르다. Python은 코드 포인트, JS는 UTF-16이다.
- `js_parity.py`로 매물 5만 2천 건과 문자열 사례, 모두 37만 7천 개를 대조했다. 다른 결과는 0건이다.
  - 대조 범위: 규칙 추출, 상태, 규칙 spec, 모델 출력 → 근거 검사 → spec, Haiku 라벨 → spec, snap, 모델 코드, 색상, 용량 등.
  - Python 쪽을 고치면 JS도 고치고 이 대조를 다시 돌린다.
- 학습 때와 다른 점이 둘 있다.
  - **입력 자르기:** 학습은 입력을 토큰 448개로 잘랐다. 브라우저에는 토크나이저가 없다. 그래서 응답의 프롬프트 토큰 수를 보고 길면 글자 수 비율로 잘라 다시 돌린다. 해당하는 글은 약 0.1%다.
  - **NFC 정규화:** HF 토크나이저는 NFC 정규화를 하고 llama.cpp는 하지 않는다. 그래서 JS에서 NFC로 맞춘다.

파일: `scripts/` (`make_train2.py`, `make_fix.py`, `run_final.sh`, `eval_gguf.py`, `js_parity.py`, `web_preds.py`), `web/` (`normalizer/`, `wllama/`, `e2e.html`)
